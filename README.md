# webOS Homebrew Repository

Один каталог для собственных IPK и приложений из внешних репозиториев Homebrew Channel.

**Страница:** <https://atlet99.github.io/webos-repos/>

**Адрес каталога:** `https://atlet99.github.io/webos-repos/apps.json`

## Подключение на телевизоре

В Homebrew Channel откройте **Settings → Add repository** и вставьте адрес каталога:

```text
https://atlet99.github.io/webos-repos/apps.json
```

## Добавить свой IPK

Выполняйте команды из корня этого репозитория. Нужны `make`, Python 3.11+ с `venv` и `pip`, `ar`, `openssl` для подписанных IPK и доступ в интернет. При первом запуске `make` создаст `.venv/` и установит зависимости; также сборке нужен доступ к внешним каталогам из `repositories.json`.

### 1. Положите IPK в `packages/`

Например, скопируйте файл `com.zona.app_3.9.53_all.ipk` непосредственно в папку `packages/`, сохранив его исходное имя. Имя файла может быть любым, главное — расширение `.ipk`. ID, версию, название и значок скрипт прочитает сам.

### 2. Положите рядом описание без номера версии

Для `packages/com.zona.app_3.9.53_all.ipk` создайте **`packages/com.zona.app.md`**. Например:

```markdown
# Моё приложение

Приложение для просмотра контента на телевизоре.

- Управление пультом.
- Сохранение настроек.

[Страница проекта](https://example.com/myapp)
```

Используйте полные ссылки `https://...` или `http://...`: Homebrew Channel открывает их в браузере телевизора. Поддерживаются заголовки, списки, выделение, ссылки и таблицы. Markdown преобразуется в HTML; Homebrew Channel очищает его от скриптов, стилей и форм.

Можно вставить ссылку обычным текстом — она станет кликабельной. Сборка автоматически добавляет в описания локальных приложений ссылку на этот GitHub-репозиторий из `origin`; в разделе Project page она используется по умолчанию, если `sourceUrl` не задан. Описания внешних каталогов остаются у их источника.

Для имени вида `название_версия_архитектура.ipk` скрипт определяет версию из IPK и ищет `название.md`. Также поддерживается описание с полным именем IPK без расширения; если есть оба файла, оно имеет приоритет. Для `myapp.ipk` используйте `myapp.md`. Файл `.md` необязателен, если описание уже есть в IPK или `packages.json`. Если описания нет, сборка сообщит имя нужного `.md`-файла.

### 3. Укажите root, если он требуется

Если приложению нужен root, создайте рядом **`packages/com.zona.app.json`**:

```json
{
  "rootRequired": true
}
```

Без этого файла считается, что root не требуется: автоматически определить это по IPK нельзя. Также в JSON можно указать `"shortDescription"` и `"sourceUrl"`. Для JSON действуют те же правила имён, что и для описания. Существующие настройки в `packages.json` по ID продолжают работать; JSON рядом с IPK имеет приоритет.

В итоге файлы выглядят так:

```text
packages/
  com.zona.app_3.9.53_all.ipk  # приложение с версией
  com.zona.app.md              # описание для всех версий
  com.zona.app.json            # необязательно: root и другие настройки
```

### 4. Проверьте и опубликуйте

```bash
make build
```

Сборка проверяет IPK, читает его данные и значок, вычисляет SHA-256 и размер, а затем создаёт страницу и каталог в `_site/`. Эту папку коммитить не нужно.

Добавьте новый IPK и созданные или изменённые файлы описания и настроек в коммит, затем отправьте изменения в `main`. После push GitHub Actions автоматически выполнит сборку и публикацию.

## Обновить свой IPK

1. Положите новый IPK с исходным именем и версией в `packages/` рядом с прежним. Для подписанного приложения добавьте также новые `.sig` и `.cert.pem`.
2. Запустите `make build` и отправьте изменения, включая удаление прежних файлов, в `main`.

Скрипт выберет наибольшую версию по данным IPK и после успешной сборки удалит старый IPK с его `.sig` и `.cert.pem`. Описание и настройки он не удаляет. Если версии нельзя однозначно сравнить или они одинаковы, сборка остановится без удаления — уберите лишний IPK вручную. Предыдущие закоммиченные версии останутся в истории Git. Очистка в GitHub Actions не меняет файлы в Git, поэтому локальную сборку и коммит удалений нужно выполнить до push.

## Подписанные IPK

Подпись необязательна. Для подписанного IPK положите рядом **оба файла из сборки приложения**:

```text
packages/com.zona.app_3.9.54_all.ipk
packages/com.zona.app_3.9.54_all.ipk.sig
packages/com.zona.app_3.9.54_all.ipk.cert.pem
```

Имена `.sig` и `.cert.pem` должны полностью повторять имя IPK с добавленным расширением. При первом добавлении подписанного приложения выполните `make build`: скрипт извлечёт ключ из сертификата, проверит подпись и автоматически запишет отпечаток в `trusted-keys.json`. Добавьте этот файл в коммит вместе с IPK. GitHub Actions не принимает новые ключи без сохранённого отпечатка: это защищает последующие автоматические сборки от незаметной подмены ключа.

Первое закрепление основано на доверии к полученному сертификату. Сверьте отпечаток с издателем по независимому каналу: самоподписанный сертификат не подтверждает личность издателя. Закрытый ключ в этот репозиторий добавлять нельзя.

При обновлении достаточно заменить три файла в `packages/`. Сборка извлечёт ключ из нового сертификата и сравнит его отпечаток с сохранённым, проверит подпись RSA PKCS#1 v1.5 с SHA-256 и то, что сертификат не просрочен. Для приложения с закреплённым отпечатком подпись и сертификат обязательны. При отсутствии файла, неверной подписи или изменении ключа сборка остановится. При смене ключа подтвердите новый отпечаток у издателя и осознанно обновите `trusted-keys.json`.

Сборка публикует IPK, подпись, сертификат и открытый ключ; ссылки и SHA-256 отпечаток DER-кодировки открытого ключа находятся в `detachedSignature` манифеста. Проверка скачанного файла вручную с **независимо проверенным** открытым ключом:

```bash
openssl dgst -sha256 -verify com.zona.app.pem \
  -signature com.zona.app_3.9.54_all.ipk.sig com.zona.app_3.9.54_all.ipk
```

Для сверки отпечатка открытого ключа с издателем: `openssl pkey -pubin -in com.zona.app.pem -outform DER | openssl dgst -sha256`.

Homebrew Channel сам проверяет SHA-256 IPK, но не проверяет эту подпись или доверие к ключу. Проверка подписи выполняется при нашей сборке и может выполняться отдельно пользователем; просто скачать ключ вместе с пакетом недостаточно для подтверждения издателя.

## Подключить внешний репозиторий

Откройте **`repositories.json`** и добавьте HTTPS-адрес его каталога `apps.json` в массив. Например:

```json
[
  "https://example.com/apps.json",
  "https://example.org/apps.json"
]
```

Сохраните существующие адреса и поставьте запятую между элементами. Затем выполните `make build` и отправьте изменённый файл в `main`.

Сборка объединяет все страницы подключённых каталогов с локальными приложениями. Внешние IPK не копируются: Homebrew Channel скачивает их по ссылке источника. Данные обновляются при сборке после push и раз в сутки по расписанию.

Если у внешнего приложения нет полного или краткого описания, создайте `descriptions/<id>.html`, как для своего IPK. Если такой файл уже существует, он заменит полное описание источника в нашем каталоге.

## Команды

| Команда | Действие |
| --- | --- |
| `make` или `make help` | Показать справку по целям Makefile. |
| `make build` или `make all` | Собрать страницу и каталог в `_site/`. |
| `make test` | Запустить тесты генератора. |
| `make lint` | Проверить Makefile через установленный `checkmake`. |
| `make python-lint` | Проверить Python-код через Ruff из `.venv`. |
| `make workflow-lint` | Проверить безопасность GitHub Actions через zizmor из `.venv`. |
| `make check` | Выполнить тесты и `checkmake`. |
| `make freeze` | Зафиксировать версии прямых зависимостей из `.venv`. |
| `make clean` | Удалить результат сборки `_site/`. |

Настройки `checkmake` находятся в `checkmake.ini`. Другой интерпретатор Python можно указать, например, так: `make build PYTHON=python3`.

В `requirements.txt` перечислены только прямые зависимости. Чтобы обновить их версии:

```bash
source .venv/bin/activate
python -m pip install --upgrade Markdown ruff zizmor packaging
make freeze
make check
```

`make freeze` записывает версии только уже перечисленных пакетов, не добавляя транзитивные и посторонние. Для новой прямой зависимости сначала установите её в `.venv`, затем выполните `make freeze PACKAGES="имя-пакета"`. Поддерживаются имена пакетов и закреплённые версии `имя==версия`; неподдерживаемые строки и отсутствующие пакеты вызывают ошибку без изменения файла. Если окружения ещё нет, сначала выполните `make build`.

## Публикация и возможные ошибки

При первоначальной настройке репозитория выберите **Settings → Pages → GitHub Actions**. Workflow **Deploy GitHub Pages** запускается после push в `main`, ежедневно и вручную через вкладку Actions. GitHub Pages получает собранный артефакт напрямую; ветка `gh-pages` не требуется.

На push и pull request workflow проверяется через `actionlint` и `zizmor`, Python-код — через Ruff, затем запускаются тесты и сборка. Публикация выполняется только после успешных проверок; pull request не публикуется.

Если сборка не прошла, проверьте сообщение в терминале или во вкладке Actions:

- **`missing description`** — для локального IPK создайте указанный `.md` рядом с ним; для внешнего приложения — указанный HTML-файл.
- **`multiple IPKs`** — найдены разные IPK с одним ID и одинаковой версией; удалите лишний вручную.
- **`duplicate package ID`** — один ID присутствует в нескольких источниках или одновременно в локальном и внешнем каталоге. Уберите повторяющийся источник или IPK.
- **Ошибка загрузки внешнего каталога** — проверьте HTTPS-адрес и доступность источника. При ошибке сборки последняя опубликованная версия остаётся доступной.

В `_site/` создаются `apps.json`, манифесты локальных приложений, страница и `SHA256SUMS`. В файл контрольных сумм входят только локальные IPK. При изменении адреса сайта задайте `BASE_URL` при локальной сборке и в workflow: это HTTPS-адрес сайта без завершающего `/apps.json`.
